Core question: What are the core components of the agent, and how do they connect during one task?

Reveal answer

The CLI resolves configuration and starts runTask. The loop builds messages, calls the model, dispatches tool calls, appends tool results, and repeats. Workspace, sandbox, hooks, memory, and UI support that loop without replacing it.

Follow-up: Which parts of the app are stateful, and where does each piece of state live?

Reveal answer

Conversation state lives in the messages array; durable knowledge lives in the memory file; files live in the workspace; effective settings live in the config object; hooks are scoped to the run. There should be no hidden global state outside those places.

Dig deeper: What is the difference between the agent loop and the program that hosts it?

Reveal answer

agent.js owns one task loop and stays unaware of flags, terminal streams, colours, and exit codes. cli.js owns process concerns: argument parsing, sessions, TTY behaviour, signals, and exit codes. The boundary is what makes the loop reusable and testable.

Dig deeper: What guarantees does the harness enforce that the model cannot bypass?

Reveal answer

Path containment for writes, command policy, tool validation and dispatch, step and output limits, and secret stripping from child environments. The model can only propose tool calls; the harness decides whether and how they execute.

01Build Prompt: mini-coding-js — a tiny Node coding-agent harness

🧭

Teaching note · the whole system

Start with the shape, not the files

The build prompt describes many files, but the architecture is one small loop. The model asks for an action, the dispatcher runs a tool, the result is appended to the message array, and the loop repeats. Everything else — workspace, sandbox, hooks, memory, config, UI — exists to make that loop safe and observable.

Core question: Why is the tool set deliberately small, and what does that buy the architecture?

Reveal answer

A small tool set keeps the action surface auditable, the schemas manageable for the model, and the safety policy centralised in one dispatcher. More tools widen the attack surface and make the loop harder to test and explain.

Follow-up: Where does the model's authority end and the harness's authority begin?

Reveal answer

The model only proposes actions as structured tool calls. The harness validates the request, applies policy, executes the tool, and returns a string observation. The model never receives direct file, process, or network authority; the dispatcher is the gate.

Dig deeper: How does the model create a file if it has no hands?

Reveal answer

It emits an assistant message containing a write_file tool call. The dispatcher validates the request, the workspace resolves the path, the tool writes the file, and the result is appended as a tool message.

Dig deeper: Why is the messages array called the state?

Reveal answer

It is the only conversation content the next model call receives. If an action, result, or instruction is not in the array, the model does not know it. Hidden state outside the array breaks that guarantee.

Dig deeper: What would break if agent.js knew about CLI flags and terminal colours?

Reveal answer

The loop would become coupled to process and presentation concerns. It would be harder to test, harder to reuse, and a CLI or UI change could force a change in agent logic.

021. workspace.js — the path policy

🗺️

Teaching note · path policy

Reads are open; writes are fenced

workspace.js teaches the difference between access and mutation. Reading docs from anywhere can be useful and is relatively low-risk; writing outside the workspace is the dangerous operation. The strict resolver normalises paths first, then checks containment, including symlink and junction escapes.

Core question: Why is rejecting ../ not enough on its own? What can a symlink do that a plain path cannot?

Reveal answer

Rejecting ../ only catches one spelling of escape. Paths can be absolute, drive-relative, UNC, expanded from environment variables, or hidden behind a symlink or junction inside the workspace. The resolver must normalise first, resolve the deepest existing ancestor with realpath, then test containment.

Follow-up: Why must ~, %VAR%, and $VAR be expanded before the containment check?

Reveal answer

A path that looks harmless before expansion can become a home or system path afterwards. Expansion first means every later check sees the real path being requested. Checking before expansion would allow an environment variable or tilde to bypass the policy.

Dig deeper: Why are resolve() and resolveRead() separate methods?

Reveal answer

They express different policies: writes are fenced, reads are deliberately open. Separate methods make the asymmetry explicit and prevent a caller from accidentally applying the wrong rule.

Dig deeper: Why resolve the deepest existing ancestor instead of the final path?

Reveal answer

The final path may not exist yet. The deepest existing ancestor is the part that can be resolved with realpath to reveal symlinks or junctions; the not-yet-created remainder is appended afterwards.

Dig deeper: What race remains even after careful path checks?

Reveal answer

Time-of-check/time-of-use: the filesystem can change between the check and the write. Path policy is best-effort against mistakes; adversarial concurrency needs OS or container isolation.

Export PathError and Workspace.

Workspace contract

  • Relative paths resolve against the workspace root.
  • rel is /-separated and is '.' for the root.
  • resolve() is the strict write policy. It must reject:
  • empty/non-string paths;
  • drive-absolute and drive-relative paths (C:\..., C:foo);
  • UNC paths (\\server\share, //server/share);
  • any absolute path;
  • paths beginning with ~, $, % that expand to a home/environment path;
  • a first segment that looks like a home/system folder: users, windows, program files, program files (x86), programdata, desktop, documents, downloads, appdata, onedrive, library, system32;
  • any path that escapes the root after realpath resolution.
  • Expand ~, %VAR%, and ${VAR} / $VAR before containment checks.
  • Symlink/junction safety: resolve the deepest existing ancestor with fs.realpathSync, then append the not-yet-created remainder. A symlink inside the workspace must not smuggle a write outside.
  • Containment test: rel === '' or rel does not start with .. and is not absolute.
  • resolveRead() deliberately does not fence reads. Absolute paths and paths outside the workspace are allowed. This is intentional: an agent must be able to read docs/logs/libraries; only mutation is dangerous. Relative reads still start at the workspace root.

The read/write asymmetry is a core lesson: reads are open; writes are fenced.

032. sandbox.js — the mutation gate

🛡️

Teaching note · mutation gate

A permission check is not a container

The sandbox is an interface, not an isolation boundary. It scans commands, applies a command policy, strips secrets from the child environment, and refuses obvious escapes. That is useful defence in depth, but it is still best-effort. Say this out loud: the honest limit is part of the lesson.

Core question: What is the difference between "we checked the command" and "the command cannot affect the host"?

Reveal answer

A command scan is a permission check: it looks at what the command appears to do and allows or denies it. A container or kernel boundary changes what the command is capable of doing. The workspace fence and deny-list are useful, but they are not the same guarantee as isolation.

Follow-up: Why strip API keys and tokens from the child environment even when the command itself is allowed?

Reveal answer

Least privilege: an allowed command still does not need the agent's secrets. Stripping keys and tokens prevents accidental printing, logging, or exfiltration through a command that was permitted for another reason. Policy and secret isolation are separate controls.

Dig deeper: What is the difference between ask, allow, and deny command policies?

Reveal answer

ask requires confirmation and denies when there is no TTY; allow runs without a prompt; deny refuses. Hard-denied commands remain refused even under --yes.

Dig deeper: Why can hard-denied commands not be overridden by --yes?

Reveal answer

They are the non-negotiable safety floor. If a convenience flag could bypass them, the policy would provide no real guarantee for demos or unattended runs.

Dig deeper: If command scanning can be bypassed, why keep it?

Reveal answer

It is defence in depth. It catches obvious mistakes, adds friction to dangerous actions, and centralises policy. It is not the sole boundary; untrusted code still needs real isolation.

Shell write-target scanning

shellWriteTargets(command) scans each command segment between separators:

  • Redirections: > and >> write to the following token. Handle 2> file where the stream number is a separate token.
  • < writes nothing; skip its operand.
  • DEST_LAST commands: copy, cp, move, mv, xcopy, ren, rename, ln, install, scp, rsync. Their last positional argument is the write target; require at least two positionals.
  • robocopy: positional argument 2 is the destination.
  • ALL_POSITIONAL commands: del, erase, rd, rmdir, rm, md, mkdir, touch, tee, unlink, truncate, shred. Every positional argument is a write/delete target.
  • Downloaders: curl output flags -o, --output, -O, --remote-name; wget -O, --output-document. For curl -O/--remote-name, the output is the URL filename (last positional).
  • PowerShell: out-file, set-content, add-content, new-item, ni, remove-item, copy-item, move-item, rename-item; target flags -destination, -dest, -path, -filepath, -literalpath. Also inspect nested cmdlets inside powershell/pwsh/ps.
  • Strip .exe, .cmd, .bat, .com, .ps1 from command names and compare case-insensitively.
  • A switch is --flag, -f, or a short Windows /x; a POSIX path like /home is not a switch.

Document the limitation honestly: this is not a shell sandbox. node -e "fs.copyFileSync(...)" or a downloaded script can still write anywhere. A container is the real answer. Do not claim otherwise.

043. tools.js — eight tools and a dispatcher

🧰

Teaching note · tools

The model proposes; the dispatcher disposes

Tools are the only way the model can act. Each tool has a schema, a handler, and a string result. Errors come back as observations rather than crashes. The dispatcher is the narrow waist: if every action passes through one function, policy and logging stay in one place.

Core question: Why return a tool error as text instead of throwing an exception that ends the run?

Reveal answer

Throwing ends the run and loses the model's chance to adapt. Returning the error as a string keeps the protocol intact: every tool call gets a result, the observation becomes part of the message history, and the model can try a different approach on the next step.

Follow-up: What makes a tool schema good enough for a model to use reliably?

Reveal answer

A clear name, a narrow argument set, obvious required fields, descriptions that explain when to use it, validation before execution, and a predictable result format. Small, boring schemas are easier for the model to call correctly and easier for the harness to check.

Dig deeper: What belongs in a tool result string?

Reveal answer

A truthful, bounded, model-readable outcome: success data, paths, errors, or refusals. It should contain enough context for the next step and must never be invented by the harness.

Dig deeper: How should the dispatcher handle an unknown tool or invalid JSON arguments?

Reveal answer

Return an error observation instead of crashing. Name the tool or parse problem clearly, and still produce a tool result so the loop can continue and the model can adapt.

Dig deeper: Why should tools not be invoked directly by the model?

Reveal answer

The model cannot execute code; it can only ask. Harness mediation provides validation, policy, logging, sandboxing, and a consistent result contract. Direct authority would remove those controls.

054. llm.js — the model call

🔌

Teaching note · model call

The model is a function with failure modes

The model call is not magic; it is an HTTP-shaped dependency that can time out, truncate, return malformed JSON, or produce no tool calls. llm.js should normalise providers and surface those states clearly so the loop can decide what to do next.

Core question: What should the loop do when the response is cut off by the token limit?

Reveal answer

Do not treat a truncated response as a complete one. Inspect the finish reason or length signal, discard or repair incomplete tool arguments, and either retry with a clear instruction or stop with an honest message. Never invent the missing arguments.

Follow-up: Why inject the chat function instead of importing a provider client directly?

Reveal answer

The loop should depend on an interface, not a vendor. Injecting the function makes it easy to swap providers, run offline with a fake model, and assert exactly which messages were sent without making a network request.

Dig deeper: What are llm.js responsibilities, and what are they not?

Reveal answer

It builds the request, calls the provider, handles timeouts and HTTP failures, and normalises the response shape. It does not orchestrate the loop, execute tools, or format terminal output.

Dig deeper: Why normalise provider responses?

Reveal answer

Providers differ in field names and tool-call representation. The loop should consume one stable shape, which reduces provider-specific branching and keeps the agent contract clear.

Dig deeper: On a timeout, should llm.js retry silently?

Reveal answer

No. Retry policy should be explicit and bounded at the caller. Silent retries can duplicate cost or side effects and hide latency; return a clear failure instead.

065. prompt.js — the system prompt

📝

Teaching note · prompt

The system prompt is rebuilt every turn

The system prompt is not a one-time greeting. It carries the rules, the current memory digest, and the contract for tool use. Keeping it in prompt.js makes it reviewable and testable, and lets memory changes appear without restarting the process.

Core question: What belongs in the prompt, and what belongs in code that the model cannot edit?

Reveal answer

The prompt carries instructions, rules, the memory digest, and the tool contract. Code carries enforcement: path containment, command policy, step limits, output caps. Anything that must be guaranteed belongs in code, not in a request the model can ignore.

Follow-up: What happens when memory changes in the middle of a session?

Reveal answer

The system prompt is rebuilt for each request, so a memory change can appear on the next model call without restarting the session. Conversation history remains, but the fresh prompt carries the current memory digest and rules.

Dig deeper: Why is the system prompt not a security boundary?

Reveal answer

It is text the model may ignore or be manipulated into overriding. Guarantees belong in code: path policy, command policy, limits, and validation. The prompt guides behaviour; it does not enforce it.

Dig deeper: What is prompt injection in this agent?

Reveal answer

Untrusted content such as file text or tool output contains instructions that try to override the system rules. Treat that content as data, keep least privilege, and enforce decisions outside the prompt.

Dig deeper: Why keep tool schemas separate from the prompt text?

Reveal answer

The schemas are a structured API contract sent with the request; the prompt describes behaviour. Mixing them duplicates information and lets the two definitions drift apart.

076. agent.js — the loop

🔁

Teaching note · the loop

The loop is the agent

Messages are the state. If something is not in the array, the model does not know it. No tool calls means the reply is the final answer. Tool calls mean append each result and go round again. A step limit turns an endless loop into a bounded failure.

Core question: Why must every tool_call_id get a matching tool result before the next model call?

Reveal answer

The provider protocol expects each assistant tool_call to be followed by a tool message carrying the same tool_call_id. Without that pairing the next request is malformed, and the model sees an incomplete record of what it asked for and what happened.

Follow-up: Why does the loop need a step limit?

Reveal answer

Without a limit, a confused model can loop forever, spend money, or flood the transcript. A step limit turns that into a bounded, observable failure with a clear reason, and it makes loop tests deterministic.

Dig deeper: Why append the assistant reply before executing its tools?

Reveal answer

The history must show what the model requested. Tool results then attach to that assistant turn through their ids. Without the assistant message, the tool messages have no preceding call.

Dig deeper: What if the model returns text and tool calls together?

Reveal answer

Preserve the text in the assistant message and process the tool calls. The text may be commentary; the reply is not final until a model response contains no tool calls.

Dig deeper: Why not automatically retry a failed tool?

Reveal answer

The failure is an observation for the model to reason about. Blind retries can repeat side effects. Any retry policy should be explicit, bounded, and owned by the caller.

087. hooks.js — lifecycle extension points

🪝

Teaching note · hooks

Hooks are observability seams

Lifecycle hooks let the program observe or intervene without putting policy inside the loop. A hook can post a note, refuse to start, or annotate a tool call. The trace is the teaching tool: students can see exactly when each moment fires.

Core question: Which hook would you use to log every model request, and which would you use to block a dangerous tool?

Reveal answer

Log every request with PreModel or PostModel; both observe the model boundary. Block a dangerous action with PreToolUse, because that fires after the model has chosen a tool but before the dispatcher executes it.

Follow-up: What does "first block wins" mean for hook handlers?

Reveal answer

The first handler that returns a block stops the action. Later handlers for that moment are skipped, and the tool or run does not proceed. The first refusal is the decision, which keeps policy order predictable.

Dig deeper: What can PostToolUse change that PreToolUse cannot?

Reveal answer

PostToolUse sees the result and may replace the observation text. PreToolUse sees the proposed call and may block it before execution. They run at different times for different purposes.

Dig deeper: Why inject hooks instead of importing a global hook registry?

Reveal answer

Injected hooks are scoped to a run, easy to test, and free of cross-test global state. A global registry makes behaviour depend on registration order and hidden setup.

Dig deeper: What is the danger of putting policy only in hooks?

Reveal answer

Hooks are optional and can be missing or misconfigured. Safety must hold by default in the core. Hooks are for observation and extension, not the only enforcement layer.

1211. heartbeat.js — liveness

💓

Teaching note · heartbeat

Liveness is not progress

A heartbeat says the process is still alive; it does not say the work is advancing. That distinction matters for watchdogs and for honest status messages. A heartbeat that keeps firing during a stuck model call is still useful information: it tells you where the stall is.

Core question: What can a heartbeat prove, and what can it never prove?

Reveal answer

A heartbeat proves the process is alive and still scheduling work. It cannot prove progress, correctness, or that a remote call is healthy. A heartbeat during a hung model request still tells you the process has not died, which is useful for locating the stall.

Follow-up: What should an external watchdog do if the heartbeat stops?

Reveal answer

A watchdog can treat the process as stalled or dead and restart or report it. The process itself may be unable to announce failure if its event loop is blocked, which is exactly why the heartbeat is external evidence, not a self-certification.

Dig deeper: Why update a timestamp instead of printing a heartbeat line every interval?

Reveal answer

A timestamp is cheap, machine-readable, and does not flood the transcript. An external watchdog can poll it while the real output stays readable.

Dig deeper: Can a heartbeat keep a hung operation alive?

Reveal answer

No. It reports liveness; it cannot unblock a hung call. Timeouts, cancellation, or an external watchdog must handle the actual stall.

Dig deeper: Where should heartbeat logic live?

Reveal answer

At the process or CLI boundary, or injected into a long-running loop as a dependency. The core agent should not depend on a specific heartbeat transport.

1514. Testing requirements

🧪

Teaching note · testing

Test the seams, not just the output

The design is testable because the dependencies are injectable: model, clock, logger, confirmation function, hooks, memory, and workspace. A fake model can drive the loop deterministically. If a feature cannot be tested offline, the boundary is probably in the wrong place.

Core question: Which dependency would you inject first to test the loop without a real model?

Reveal answer

Inject the model first. A fake model can return a scripted tool call followed by a final answer, which drives the loop deterministically without a network key. The clock, logger, confirmation function, hooks, memory, and workspace can then be added as needed.

Follow-up: What is a fake model, and what should it record?

Reveal answer

A fake model is a function with the same interface as the real chat call, returning canned responses. It should record the messages it received and the order of calls so tests can assert what the loop sent and when.

Dig deeper: What should be tested with a fake model versus a real temporary filesystem?

Reveal answer

Use a fake model for loop protocol, ordering, and termination. Use real temporary directories for workspace resolution, sandbox writes, and memory persistence. Integration tests combine both at the boundaries.

Dig deeper: Why must the write fence and command policy have negative tests?

Reveal answer

Refusals are the safety contract. Tests must prove that an outside write returns FORBIDDEN without touching disk, that a hard-denied command never runs, and that a denied confirmation has no side effect.

Dig deeper: Which dependencies must be injected to make the agent loop deterministic?

Reveal answer

At minimum the model, clock, logger, confirmation function, hooks, memory, and workspace. Temporary directories and fixed inputs remove filesystem and timing variation; no test should depend on network access or shared global state.

1716. Acceptance criteria

✅

Teaching note · acceptance

Definition of done is behavioural

Acceptance criteria should describe observable outcomes: a refusal prints one line, a write outside the workspace returns an observation, a session survives a restart. Features are not done because they exist; they are done when the promised behaviour can be checked.

Core question: Which acceptance criterion would catch a regression in the write fence?

Reveal answer

The clearest criterion is the write-fence test: attempt a write outside workspace/, confirm one FORBIDDEN line and a returned observation, and verify that no file was created. That catches regressions in path resolution, policy, and tool behaviour together.

Follow-up: Why should acceptance criteria be observable at the CLI level?

Reveal answer

The CLI is the user-facing contract. Observable criteria catch integration failures that unit tests can miss, and they can be checked without knowing internal function names. If the behaviour cannot be observed from outside, it is hard to call it done.

Dig deeper: What exit code should a run return when it hits the step limit, and why?

Reveal answer

The specified step-limit exit code should be distinct from success, usage errors, and missing-key failures. It lets scripts and tests distinguish "the agent stopped because it ran out of budget" from other failure modes.

Dig deeper: What observable evidence should the acceptance suite require for a blocked command?

Reveal answer

A refusal line, a returned DENIED observation, no command side effect, and the expected hook trace or exit behaviour. The test should fail if any of those are missing.

Dig deeper: Which sandbox failure paths must acceptance cover?

Reveal answer

An outside write, a hard-denied command under --yes, an ask policy with no TTY, a blocked PreToolUse hook, and a child environment without secrets. These are the behaviours that define the safety contract.

Teaching note · build order

Build the boundaries before the intelligence

The suggested order starts with path policy, presentation, sandbox, memory, prompt, tools, model, hooks, loop, demo, config, and CLI. Boundaries come first because every later file depends on them. The loop is easier to write when the world around it is already trustworthy.

Core question: What goes wrong if you build the agent loop before the workspace and sandbox contracts?

You get a loop that can act before the world around it is trustworthy. Writes, reads, command policy, and tool results are all undefined or unsafe, and tests become coupled to whatever behaviour happens to emerge. Contracts first make the loop small and predictable.

1918. Tone and design philosophy (important)

🎓

Teaching note · philosophy

Small enough to explain

The final constraint is not a feature; it is a design principle. Resist additions that make the system harder to hold in your head. Put each decision in one obvious place, prefer observable behaviour over magic, bound autonomy, and be honest about safety limits.

Core question: Which additions would violate the project’s bounded-autonomy constraint?

Reveal answer

Arbitrary shell execution without policy, unbounded loops or output, automatic dependency installation, a hidden memory index, or multi-agent orchestration without explicit limits. Each adds authority or state the harness cannot reliably bound.

Follow-up: What constraints must any new feature satisfy without breaking the architecture?

Reveal answer

It must have one obvious place, remain testable offline, respect existing path and command policy, avoid hidden global state, stay within bounded limits, and not make the core loop harder to explain or observe.

Dig deeper: Why is hidden global state a problem for the agent’s behaviour and tests?

Reveal answer

It makes behaviour depend on prior runs or module load order, so the same messages can produce different results. Explicit state passed through runTask keeps behaviour reproducible and lets tests control every input.

Dig deeper: What does bounded autonomy mean in practice?

Reveal answer

Limits on steps, time, output, memory, command policy, and permissions. The agent can act, but it cannot run forever, spend without bound, or escape its defined scope.

Dig deeper: What safety claims must the project avoid making about its sandbox?

Reveal answer

It must not claim container-level isolation, complete command safety, or that the deny-list cannot be bypassed. It should state that the workspace fence and command scanner are best-effort and that untrusted code needs a real external boundary.

  • Small enough to explain. One loop, eight tools, nine hooks. Resist adding features.
  • One obvious place for each decision. Config in config.js, path policy in workspace.js, mutation gate in sandbox.js, prompt in prompt.js, presentation in ui.js, process concerns in cli.js.
  • Observability over magic. Every step, tool call, result, hook firing, and refusal is visible in the terminal.
  • Bounded autonomy. Step limits, output caps, timeouts, per-entry memory caps, prompt-memory budgets, and a deny-list all exist because "autonomous" without bounds is a bug.
  • Honest safety. The workspace fence and shell write scanner are useful but not a container. Say so in code comments and docs.
  • Human in the loop. Default command policy is ask; no TTY means deny; hard denies cannot be overridden.
  • Testable by construction. Inject the model, clock, logger, confirm function, hooks, memory, and workspace. If a feature cannot be tested offline, the seam is wrong.
  • Teachable error strings. A refusal, a failed exit code, and a missing key must explain what happened and what to do next.
  • No fake results. The system prompt forbids invented tool results, and every tool observation is a real string produced by the harness.
  • Memory is a file you can read and diff. No vector store, no embeddings, no hidden index. A student can open src/memory.md and see exactly what the agent knows.
