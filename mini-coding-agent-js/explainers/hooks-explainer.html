Lifecycle hooks, in nine moments

A fixed loop is readable, but not extensible. This is the smallest extension point that fixes it: a function attached to a named moment, called by the loop, able to observe, rewrite, or block. Ten scenes, about two minutes, no key and no network.

A hook does not call the model and does not run tools. It is a pure function of the payload.

06

The deciding hooks

Two verbs that change the run.

BLOCKPreToolUse
tool callgit push origin main
hook{ block: true, reason: 'no pushes' }
model seesDENIED: ... Try another approach.

The tool never runs. The model gets the refusal as an observation and can choose another way.

REPLACEPostToolUse
tool outputOPENAI_API_KEY=sk-or-abc123
hook{ replace: '... sk-or-[redacted]' }
model seesOPENAI_API_KEY=sk-or-[redacted]

The result exists and the model has not seen it yet. Replace it: redact, cap, or annotate a failure.

A refusal is an observation, not an exception. The loop cannot crash on a “no”, and the model gets another turn.
07

How a run ends

Every path ends in the finally block.

🏁Stop

the model answered and the loop is ending answer · steps · messages

A summary, a cost report, or the notification that says the job is done.

⏳StepLimit

the loop hit maxSteps without an answer steps · messages

Failures need a lifecycle too: escalate, or dump the transcript for a post-mortem.

whichever way it went

🔒SessionEnd

always — finished or not ok · reason · steps · durationMs · messages

One place that runs whatever happened is what makes cleanup, timing and audit logs reliable rather than hopeful.

08

The registry

A map, a list, and one answer.

src/hooks.jsrun
for (const handler of [...handlers]) {
  try {
    decision = await handler.fn(payload, { event });
  } catch (err) {
    out.errors.push(`${handler.id}: ${err.message}`);
    continue; // one bad hook is not the loop's problem
  }
  if (!decision || typeof decision !== 'object') continue;
  if (decision.block) { out.blocked = true; break; }
}
handlers run in registration order
A{ note: 'checked' } → collected
Bthrows → reported, ignored
C{ block: true } → first refusal wins
Dskipped — no second opinion
what run() returns
{ event: 'PreToolUse', ran: 3, blocked: true, reason: 'no pushes',
  notes: ['checked'], errors: ['B: boom'] }
Above all, every tool_call still gets a matching tool result — or the next request would be invalid.
09

Putting it to work

A permission layer in twelve lines.

1Permission layer

hooks.on('PreToolUse', ({ name, args }) =>
  name === 'run_command' && /\bgit push\b/.test(args)
    ? { block: true, reason: 'no pushes' }
    : undefined
);

The model asks. The hook decides.

2Redaction

hooks.on('PostToolUse', ({ result }) => ({
  replace: String(result)
    .replace(/sk-or-\S+/g, 'sk-or-[redacted]')
}));

Whatever was printed, a key never reaches the model.

3Cleanup

hooks.on('SessionEnd', ({ ok, reason,
                        durationMs }) => ({
  note: `run ${ok ? 'ok' : reason} in ${durationMs}ms`
}));

Failures get a lifecycle too.

what the model sees
tool → run_command {"command":"git push origin main"}
result ← DENIED: a PreToolUse hook blocked this call (no pushes). Try another approach.
